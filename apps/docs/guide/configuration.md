# Instance settings

**Settings** at the bottom of the sidebar holds the everyday configuration for this instance. A save writes to the database and reaches the Runtime in the next snapshot; it does not require an application rebuild.

The page is divided by the job each setting performs.

## Runtime

This section controls public-facing behavior:

- **Canonical Runtime URL** is used for QR codes and public links generated by the interface;
- **Robots policy** decides whether well-behaved crawlers may index Runtime responses;
- **Configuration cache** and **rule cache** decide how often the Runtime checks for a new snapshot.

Shorter caches make saves appear sooner, but make every Runtime contact the WebUI more often. A personal instance rarely needs very low values. When a saved rule still returns the old result, check the rule-cache value here first.

## Analytics

The ingest endpoint normally ends with `/api/analytics/events` on the WebUI. The source ID identifies the whole instance with a base domain such as `i0c.cc`; it is not a provider name such as `cloudflare` or `vercel`.

Several Runtimes may share one source ID. Analytics records the actual entry domain and provider separately. Disabling the analytics plugins does not stop rules from working, but no new events will be stored.

## WebUI access

The access mode controls who may enter the console:

- **Any signed-in GitHub user** admits every signed-in account except blocked IDs;
- **Managers only** admits only IDs in the manager list;
- **GitHub users read-only, managers can edit** lets ordinary signed-in users view while managers save; blocked IDs are denied.

The lists use numeric GitHub user IDs because usernames can change. The same ID cannot be both a manager and blocked.

## Installed plugins

This page lists the plugins that were bundled into the WebUI or Runtime at build time. Open one to see its purpose, current status, public settings, and required environment bindings.

Disabling a plugin changes instance configuration; it does not delete an external deployment. Runtime platform adapters deserve particular care: if a provider project still receives traffic after its adapter is disabled, that deployment enters its error fallback. Remove or retire the provider project separately when you no longer want it.

The settings page cannot install code. A new Runtime, database adapter, or feature plugin still has to be added to the workspace and included in a new build.

## Data and history

Use this section to export the current settings and rules, import a backup, inspect old revisions, or restore an old revision as a new active version.

A restore never rewrites the earlier history. Before importing or restoring, resolve any unsaved rule or setting edits so that two changes are not mixed together.

## Why secret fields contain names

Plugin settings store environment-variable names:

```json
{
  "secrets": {
    "writeKey": "I0C_SECRET"
  }
}
```

This means “read the secret from `I0C_SECRET` at runtime.” It does not store the secret value in the database. Actual values stay in the WebUI, Runtime, or database provider's environment settings.

## Choices that are not editable here

Some values must exist before an application can read the database, so they remain in `packages/config/src/defaults.ts`:

- whether PostgreSQL, D1, or GitHub stores rules and settings;
- whether the Runtime reads an HTTP Snapshot or GitHub Raw;
- which analytics storage plugin is bundled;
- D1 Account and Database IDs;
- the GitHub OAuth scope.

The application reads these choices at startup; together they form the bootstrap configuration. Changing them requires a rebuild. Actual secret values still do not belong in that file.

The WebUI validates a save against the shared Schema and every installed plugin requirement. Fix the named section when a field is rejected. Revision checks also prevent an old browser tab from silently overwriting a newer saved version.
