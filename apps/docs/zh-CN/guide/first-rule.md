# 创建第一条规则

下面用刚部署好的 Runtime 完成一次跳转，结果如下：

```text
https://go.example.com/docs  →  https://docs.example.com
```

把两个示例域名换成自己的 Runtime 域名和一个可以正常打开的目标地址。

## 继续前确认

确认下面几项已经完成：

- WebUI 可以登录并进入规则页面；
- 当前 GitHub 账号有编辑权限；
- 一个 Runtime 已经部署，并绑定了公开域名；
- WebUI 与 Runtime 使用相同的 `NAMI_SECRET`。

如果公开域名现在显示 nami 的 404 页面，正适合继续。它说明请求已经进入 Runtime，只是还没有规则。

## 1. 打开规则分组

进入 WebUI 的**规则**页面，在左侧选择 `Main`。分组只是帮助你整理规则，不会出现在公开 URL 中。

点击右侧的**新增规则**。

<!-- 需要真实截图：规则页选中 Main，并显示“新增规则”按钮。 -->

## 2. 填写跳转

在弹窗中填写：

```text
路径：/docs
描述：项目文档
匹配类型：exact
目标地址：https://docs.example.com
状态码：302
```

`exact` 表示只匹配 `/docs`。`/docs/setup` 不会跟着命中。第一次测试使用 `302`，这样浏览器不会像永久跳转那样长期缓存结果。

统计 ID 由 WebUI 自动生成，不需要修改。以后更换路径或目标地址时保留它，统计历史仍会认作同一条规则。

<!-- 需要真实截图：新增规则弹窗已填好上面的示例值。 -->

## 3. 保存

点击**保存规则**，等待右下角出现“保存成功”。默认的数据库存储会立即创建一个新修订，规则卡片也会出现在 `Main` 中。

卡片应该显示目标地址、`/docs` 路径和 `exact` 类型。如果关闭弹窗后没有卡片，先看通知内容，不要重复点多次保存。

<!-- 需要真实截图：保存后的规则卡片与成功通知。 -->

## 4. 等待 Runtime 读到新快照

Runtime 不会在每个请求上重新获取数据库内容。默认规则缓存时间是 60 秒，因此刚保存后的短暂旧响应并不一定是故障。

等一个缓存周期后，在浏览器打开：

```text
https://go.example.com/docs
```

成功时，地址栏会进入 `https://docs.example.com`。

## 5. 看一眼原始响应

浏览器会自动跟随跳转。想确认 Runtime 自己返回了什么，可以运行：

```sh
curl -I https://go.example.com/docs
```

响应应包含 `3xx` 状态和目标地址：

```text
HTTP/2 302
location: https://docs.example.com/
```

这里不要加 `-L`，否则 curl 会继续请求目标网站，你看到的就不再是 Runtime 的原始响应。

## 没有生效时先查什么

- 仍然看到 Runtime 404：检查路径是否以 `/` 开头，以及 Runtime 是否已经刷新快照；
- 一直得到旧结果：检查 `snapshotUrl` 是否指向自己的 WebUI，以及两端密钥是否一致；
- 浏览器结果奇怪但 curl 正常：可能是浏览器缓存了之前的永久跳转，换无痕窗口再试；
- 平台返回 500 或 Bad Gateway：先看 Runtime 日志中的快照加载和必需插件错误。

第一条规则跑通后，再阅读[管理规则](/zh-CN/guide/rules)，了解前缀跳转和透明反代。设置入口见[实例设置](/zh-CN/guide/configuration)。
